1. NEW API ENDPOINTS IMPLEMENTED
--------------------------------------------------------------------------------
All endpoints are available at `/api/auth` (and mirrored at `/api/v1/auth`):

• POST /api/auth/register
  - Public endpoint.
  - Registers a new user.
  - Input: { name, email, password, phone? }
  - Enforces `role: 'USER'` (neutralizes client tampering / privilege escalation).
  - Validates email format, required name, password >= 6 characters.
  - Checks duplicate email (returns 409 Conflict if registered).
  - Hashes password using bcrypt (10 salt rounds).
  - Issues signed JWT and returns 201 Created with safe user profile (no password).

• POST /api/auth/login
  - Public endpoint.
  - Authenticates user credentials.
  - Input: { email, password }
  - Normalizes email (lowercase, trimmed).
  - Verifies bcrypt password hash against stored record.
  - Returns generic 401 Unauthorized ('Invalid email or password') on failure
    to eliminate username enumeration.
  - Returns 200 OK with safe user profile and signed JWT on success.

• GET /api/auth/me
  - Protected endpoint requiring Bearer JWT.
  - Header: Authorization: Bearer <token>
  - Verified by `authenticate` middleware.
  - Returns 200 OK with the authenticated user's safe profile.

3. SECURITY & SYSTEM DESIGN HIGHLIGHTS
--------------------------------------------------------------------------------
1. No Plaintext Passwords:
   - Password hashing is enforced via bcryptjs with 10 rounds.
   - Plaintext passwords are never logged, stored, or sent in response payloads.
2. Privilege Escalation Prevention:
   - Registration explicitly sets `role: 'USER'`, ignoring any client-sent `role`.
3. Safe User Serialization:
   - `toSafeUser` ensures the password hash is excluded from all JSON responses.
4. Information Disclosure Mitigation:
   - Login failure responds with a generic `INVALID_CREDENTIALS` code and message,
     preventing attackers from guessing whether an email exists.
5. Fail-Fast Environment Configuration:
   - `JWT_SECRET` and `JWT_EXPIRES_IN` are verified at boot time via `env.js`.
6. Prisma 7 Driver Adapter Compatibility:
   - In Prisma 7, PostgreSQL connections require the `@prisma/adapter-pg` driver
     adapter. Initialized cleanly in `db.js`.

5. POSTMAN / MANUAL TESTING INSTRUCTIONS
--------------------------------------------------------------------------------
To test manually once the server is running (`npm run dev` in `server/`):

Step 1: Register User
• Method: POST
• URL: http://localhost:5000/api/auth/register
• Headers:
    Content-Type: application/json
• Body (JSON):
    {
      "name": "Bruce Wayne",
      "email": "bruce@waynecorp.com",
      "password": "batmanpassword123",
      "phone": "9998887776"
    }
• Expected Status: 201 Created
• Copy the "token" value from response.data.token.

Step 2: Login User
• Method: POST
• URL: http://localhost:5000/api/auth/login
• Headers:
    Content-Type: application/json
• Body (JSON):
    {
      "email": "bruce@waynecorp.com",
      "password": "batmanpassword123"
    }
• Expected Status: 200 OK

Step 3: Get User Profile (Protected)
• Method: GET
• URL: http://localhost:5000/api/auth/me
• Headers:
    Authorization: Bearer <paste_token_here>
• Expected Status: 200 OK
• Response Body:
    {
      "success": true,
      "data": {
        "user": {
          "id": "...",
          "name": "Bruce Wayne",
          "email": "bruce@waynecorp.com",
          "phone": "9998887776",
          "role": "USER",
          "createdAt": "...",
          "updatedAt": "..."
        }
      }
    }
